How to show Jira Service Management Assets to customers in the portal

Your team keeps devices, licenses and contracts in Assets. Your customers raise requests about exactly those things. Yet in the portal they usually can't see any of it. This guide shows what works out of the box and where an app helps.

November 17, 2026 · BasicData

Option 1: An Assets field on the request form

Jira Service Management can show Assets objects on a portal request form. You add a custom field of type "Assets objects" to the request type. With the field's Filter issue scope (AQL) you limit the list to objects that belong to the person raising the request.

The object needs a user attribute that holds the customer's Atlassian account. If that attribute is called Owner, the filter looks like this:

"Owner" = currentReporter()

Many admins use the placeholder form instead:

"Owner" = ${reporter}

When a customer opens the form, the dropdown then lists only their own objects. The selected object is linked to the ticket, so agents see the affected asset right away.

Set up the field configuration first

The field needs a complete Assets field configuration. Assign the object schema and set the searchable attributes in Jira administration under Issues, Custom fields, your Assets field, Configure. The field also has to be on the screens of the service project. If this is missing, linking fails with the error cmdb.config.not.found.

Check ownership in your data

The filter only works as well as your data. Every object a customer should see needs the right account in its owner attribute. Typical gaps are objects without an owner and rehired employees with a new Atlassian account. Many schemas also store the user on a linked record, such as an Employee object that the laptop references. Plan the AQL for that case and test it with a real customer account.

Where the native setup stops

The Assets field is a selection list inside one form. That covers the moment of raising a request. Customers often need more than that:

  • There is no page where a customer sees everything assigned to them. They only see their objects while filling in a form.
  • Customers can't see attributes such as status, serial number or renewal date before they decide what to report.
  • Customers can't correct or update data themselves. Every change goes through an agent.
  • Each request type needs its own field setup. Ownership logic is repeated in several places.

For a few request types this is fine. If you want customers to work with their assets in the portal, you need a dedicated view.

Option 2: A My Assets view in the help center

Apps on the Atlassian Marketplace can add a page to the customer portal. We built Customer Assets for the JSM Portal for exactly this. It adds a "My Assets" entry to the portal user menu. Customers see the objects assigned to them, with the attributes you choose.

From each asset, customers can report a problem, ask a question or request a change. The app creates a normal Jira Service Management request with the asset already linked. Per object type you decide whether customers may edit directly, submit change requests or only view.

The ownership logic is the same as in option 1. You map an owner attribute per object type, or a path through a linked object such as Employee -> User. The app checks ownership on the server for every query and shows nothing it can't prove belongs to the signed-in customer. It runs on Atlassian Forge, so asset data stays on your site.

Try it on your data. Every new subscription starts with a 30-day free trial. The setup guide walks you through the four configuration steps.

Which option fits

Use the Assets field if customers only need to pick an asset while raising a request. It costs nothing and you can set it up in an hour. Add a My Assets view if customers should see, check or update their assets in the portal. Both options rely on the same thing: a clean owner attribute on every object. Start there either way.
