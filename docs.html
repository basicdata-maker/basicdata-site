Overview #

Customer Assets for the JSM Portal gives your customers a secure self-service view of their assigned assets (JSM Assets / Insight) inside the Jira Service Management help center. Customers see exactly the devices, licenses and other objects assigned to them, edit what you allow them to edit, and raise asset-linked requests: report a problem, register an asset, request a change or ask a question.

Not sure what to model beyond IT hardware? The use cases page shows how the same pattern works for licenses, fleet, facilities, MSP customer portals, rental, education and healthcare.

Getting started #

Requirements

Before you configure anything, make sure you have:

  • Jira Service Management Cloud with Assets (Premium or Enterprise). The app reads your existing Assets (CMDB) data; it does not bring its own database.
  • An asset schema with an owner per object type. Ownership is either a user attribute on the object itself, or an object reference to a linked object (for example an Employee record) that carries the user attribute. The app auto-suggests likely candidates, including linked-object paths.
  • A JSM project with request types the app can use for asset requests (problems, questions, registrations, change requests).
  • An "Assets objects" custom field to link tickets to assets (see the prerequisite box below).
  • Site-admin permissions for configuration.
Mandatory prerequisite: Assets field configuration. The Jira custom field of type "Assets objects" links tickets to assets. It needs a complete Assets field configuration: assign your object schema and set the searchable attributes (ideally including Key) in Jira admin → Issues → Custom fields → your Assets field → Configure. The field must also be on the screens of the target project. Without this, asset linking fails with cmdb.config.not.found. The built-in check ("Verify field" in step 2 of the configuration) detects exactly this case and tells you what to fix.

Setup in 4 steps

1Open the configuration

After installing, go to Jira administration → Apps → "Customer Assets — Configuration". On first run the setup wizard starts automatically, with a contextual help panel and an illustrated example at every step. The admin page also shows a setup status panel: four plain-language health checks (asset database, owner mapping, Jira asset field, reporting paths), each with a fix button that takes you to the right place.

In a hurry? The wizard's automatic suggestion scans your service project and asset database and fills in all four steps with one click. You only review the result.

2Connect tickets

Pick your JSM service desk and the request types for asset issues and asset registrations, and select the Assets custom field used to link the affected asset. Then click "Verify field". It checks field existence, type, screen assignment and the Assets field configuration end to end.

3Connect assets

Choose your object schema and the object types customers should see. For each type, confirm the auto-suggested owner attribute; it scopes every query to the signed-in customer. If ownership lives on a linked object, use the path notation Reference attribute -> User attribute, for example Employee -> User. The suggestions include these paths automatically.

While you map owners, a live preview shows what the portal would list for you with the current, still unsaved selection. If your own assets appear, the mapping is right.

4Shape the experience

Per object type you set card attributes, a status attribute with color mapping, visible detail attributes, editability (direct edit, change request or read-only) and icons. You can also add portal languages and translate object-type and attribute names. An optional dashboard start view (counters, status distribution, recent updates, quick actions) can be enabled globally.

Configuration is stored in Forge Key-Value Storage on your own site and can be changed anytime without redeploying. "Reset configuration" in the admin page wipes it completely.

Core concepts #

Ownership and the owner attribute

Everything in the app revolves around one question: which Atlassian account does this object belong to? The answer comes from the owner attribute you configure per object type. It must be (or lead to) a user-type attribute that holds the customer's Atlassian account. When a customer opens the portal, the app looks up objects whose owner attribute matches their account, and nothing else.

Ownership via a linked reference object

Many schemas do not store the user directly on the asset. Instead, a Laptop references an Employee object, and the Employee object carries the user attribute. The app supports this with a two-step owner path: Reference attribute -> User attribute, for example Employee -> User or Contact -> User. Resolution happens server-side with the same scoping guarantees as a direct attribute. You can mix both styles across object types in one configuration.

The visibility model: default-deny

The app never shows an object unless it can positively prove ownership:

  • Every resolver call takes the customer's identity from the signed Forge context, never from the frontend, and wraps every AQL query in a scope-binding predicate.
  • No resolvable account ID means an empty result set, even against a manipulated frontend.
  • Object types you have not enabled in the configuration are invisible, full stop.
  • Updates are re-authorized server-side before anything is written.

In short: if the configuration or the data does not explicitly connect an object to the signed-in customer, the customer does not see it.

Configuring the portal experience #

All presentation settings live in step 4 of the configuration and are set per object type, so laptops can look different from licenses.

Card attributes. Choose which attributes appear on the asset card in the list view. Pick the few that let a customer recognize the object at a glance, such as model, serial number or renewal date.

Status badge and colors. Select one attribute as the status attribute and map each of its values to a badge color. Customers then see at a glance whether something is active, in repair or due for return. The mapping references status values by name, so keep it in sync when you rename statuses in the schema (see Troubleshooting).

Detail view attributes. Decide which attributes the detail view shows, and in which order. You can expose more here than on the card. Attributes you leave out stay hidden from customers entirely.

Translations. Object-type and attribute names come from your schema, which is often internal jargon. You can translate both per portal language, so "NB-HW-Pool" can appear as "Laptop" to customers.

Languages. The app UI ships in English and German and follows each user's Atlassian profile language. You can add portal languages for your translated type and attribute names in the configuration.

Dashboard start view. Optionally, customers land on a dashboard instead of the plain list: asset counters, status distribution, recently updated objects and quick actions. Enable or disable it globally.

Tickets and request types #

The app turns asset context into ordinary JSM requests, so your agents keep working in the tools they know.

Report a problem. From any asset, the customer opens a problem report. The ticket is created with your configured request type and the asset already linked in the Assets custom field.

Ask a question. Same flow, different request type: for anything that is not a defect, such as "can I get a second charger for this?".

Change requests. When an object type is set to change request editability, a customer's edit does not touch the object. Instead the app raises a ticket that describes the requested change; your team reviews it and applies it (or does not). The asset is linked, so the agent sees exactly what the change refers to.

Register an asset. Customers can request a new asset. By default this also raises a ticket for your team, keeping data quality and the audit trail in your hands.

How the asset gets linked. All of these tickets are created with the affected object set in the "Assets objects" custom field you configured in step 2. That is why the field's own Assets field configuration is a hard prerequisite.

Routing. You choose the service desk and the request type per flow in step 2, so problems, questions, registrations and change requests can land in different queues with different workflows and SLAs. Agents also see the reporter's assets in the "Reporter Assets" glance in the issue view.

Editing and creating assets #

Per object type, you pick one of three editability modes:

  • Read-only. Customers can view the object and raise tickets about it, nothing more. A good default for anything your team must control tightly.
  • Change request. Customers submit edits as reviewed tickets. Nothing changes in Assets until an agent applies it. Use this for attributes where you want a human in the loop, such as license cancellations.
  • Direct edit. Customers edit the allowed attributes themselves and the change is written to Assets immediately, after server-side re-authorization. Use this for low-risk, customer-owned data such as a device nickname or location.

Who may create objects? "Register asset" raises a ticket by default. Per object type you can alternatively allow direct creation by customers. Either way, customers can only ever create or edit objects within the types and attributes you expose; the schema itself stays under admin control.

Troubleshooting #

The portal shows a subscription notice instead of assets.

The app has no active subscription on this site. A Jira admin can start or manage the subscription in Atlassian Administration under Billing. New installs include a 30-day free trial; during the trial all features are available.

The portal stays empty for every customer.

Open the admin configuration and check the setup status panel: it tells you which of the four checks fails. The two usual causes are an unfinished owner mapping (step 3) and an Assets field configuration problem (run "Verify field" in step 2).

An attribute is missing on the asset card or detail view.

Card and detail attributes are selected per object type in step 4. If an attribute was added to the schema later, re-open step 4 and add it to the visible attributes.

Configuration changes do not seem to apply.

Changes are saved to Forge storage and take effect immediately; no redeploy or reinstall is needed. Ask the customer to reload the portal page. If the effect is still missing, check that you edited the object type the customer is actually looking at.

A renamed status or attribute broke colors or card labels.

The app references status values and attributes by name. If you rename a status value or an attribute in the Assets schema, the old name in the configuration no longer matches: status badges fall back to a neutral color, and renamed attributes disappear from cards and detail views. Re-open step 4 for the affected object type, re-select the attribute under its new name and re-map the status colors.

One specific customer sees the wrong assets, or someone else's.

The owner attribute on those objects points at the wrong account. Open the objects in Assets and check the user stored in the owner attribute (or, for linked ownership, the user on the referenced Employee/Contact object). Common causes: a rehired employee with a new Atlassian account, or an owner path that points at a manager attribute instead of the user attribute. The live preview in step 3 helps you verify the mapping with real data.

A customer cannot find "My Assets" in the help center.

"My Assets" is opened from the customer portal user menu (the avatar), not from the request-type tiles. Ask the customer to sign in first; anonymous visitors do not get the menu entry. If it is still missing, confirm the app is installed and subscribed on this site and that the configuration has been saved at least once.

Translated names are not showing.

Translations apply per portal language and follow each user's Atlassian profile language. If a customer still sees schema names, check that a translation exists for exactly their language in the configuration, and that it was saved for the right object type. The app UI itself is available in English and German; for other profile languages the UI falls back to English while your type and attribute translations still apply where defined.

FAQ #

Does any asset data leave our Atlassian site?

No. The app runs entirely on Atlassian Forge, has no external endpoints and qualifies for the "Runs on Atlassian" badge. Asset data is read at request time, scoped to the signed-in customer, and never copied or sent anywhere. See Data storage & privacy.

What exactly can a customer see?

Only objects of the types you enabled, and only those whose configured owner attribute resolves to their own Atlassian account. The check runs server-side on every query, default-deny. Attributes you did not add to the card or detail view stay hidden.

What does it cost, and how does the trial work?

The app is paid via Atlassian: flat USD 5/month for sites with up to 10 users, then USD 0.50 per user per month. Every new subscription starts with a 30-day free trial with all features, managed entirely through Atlassian billing. No card, no separate account.

Can we use more than one object schema?

The configuration connects one object schema with as many object types as you like, each with its own owner mapping and presentation. If you keep, say, IT and Facilities data in separate schemas, consolidate the customer-facing types into the connected schema or get in touch; multi-schema support is a request we track.

Is this "Insight" or "Assets"?

Both names refer to the same Jira feature: Atlassian renamed Insight to Assets. The app works with Assets in JSM Cloud Premium and Enterprise. Our docs say Assets; everything applies if you still call it Insight.

What happens when the "Verify field" check fails?

Follow the message shown for the failing check. It points at a wrong field type, a missing screen assignment in the target project, or an incomplete Assets field configuration. The last one is the most common cause of cmdb.config.not.found; see the prerequisite box under Getting started.

Does the app create Insight/Assets objects directly?

"Register asset" raises a ticket for your team by default, keeping data quality and audit trail in your hands. Per object type you can alternatively allow direct creation and editing by customers.

Are there performance or size limits?

The app queries Assets live via scoped AQL, so portal lists reflect your data without a sync step. Very large per-customer result sets are paginated in the portal. Forge and Assets platform limits (API rate limits, Forge execution limits) apply as on any Forge app; in normal use customers hold tens of assets, not thousands, and the portal stays fast.

Which languages are supported?

The app UI ships in English and German and follows each user's Atlassian profile language. Object-type and attribute names can be translated per portal language in the configuration.

Can customers see assets owned by their whole organization, not just themselves?

Today ownership is per person, including via a linked person record such as Contact -> User. Organization-wide ownership is on our roadmap; if you need it, tell us about your setup via the support portal so we can prioritize and design it around real cases.

Data storage & privacy #

The configuration lives in Forge Key-Value Storage on your own Atlassian site. Asset data stays in JSM Assets: the app reads it at request time, scoped to the signed-in customer, and keeps no copies. There are no external endpoints and no data egress, which is why the app qualifies for the "Runs on Atlassian" badge. Details are in the privacy policy.

Support #

The fastest way is a ticket in our support portal; we respond within one business day. Alternatively use the contact form. Please include your site URL (no credentials!), the app version and, for configuration issues, a screenshot of the "Verify field" result.
